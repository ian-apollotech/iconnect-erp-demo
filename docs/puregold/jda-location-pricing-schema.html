JDA / Blue Yonder · Logical Data Model

How JDA models Chain → Zone → Store

Puregold's Company → Zone(format) → Store is a configuration of a much more flexible schema — not the schema itself. In JDA-lineage systems (JDA MMS / Blue Yonder Merchandise Operations), "Zone" is a many-to-many price-zone membership and store format is a location trait — so the same data model supports format, geography, tier, and competitive zones simultaneously.

The three price-event levels in the spec — Chain / Zone / Store — are not three fixed org tiers. Chain resolves to the COMPANY row, Store to a LOCATION row, and Zone to any ZONE row in any zone group. That indirection is the whole source of the flexibility.

01The two things that make it flexible

Everything hinges on two structures that Puregold's usage never exercises:

  • Price zones are a many-to-many membership, not a hierarchy tier. ZONE_GROUP → ZONE → ZONE_LOCATION means a store joins a zone within a group, and can belong to many groups at once — one for format, one for region, one for competitive tier. A price event points at a zone_id from any group.
  • Store format is a location trait. "Price Club / Extra / Minimart" is one TRAIT_TYPE ("Format") among many. Traits classify without consuming the org hierarchy, so geography stays available as a separate axis.

Because of this, JDA does not have to pick "format" or "geography" as the middle level — it holds both, and a price event simply targets whichever ZONE it needs.

02How Puregold configures it

Puregold lights up exactly one zone group and uses format as its pricing axis. Nothing in the spec is wrong — it's just a narrow instantiation of the model above:

Zero schema change Adding geography is a data insert, not a redesign

To get regional pricing, you don't touch the model — you add one ZONE_GROUP "Region" with zones NCR · N.Luzon · S.Luzon · Visayas · Mindanao, then rows in ZONE_LOCATION mapping each store to its region.

Now a single store is simultaneously Format = Price Club and Region = NCR. A price event can target the format zone or the region zone — so a Price Club in Davao can be priced differently from one in Manila without dropping to individual Store level. That is exactly the capability the geographic-zone question is about.

The reconciliation Spec vs. schema, resolved

The spec isn't in conflict with the schema — it's a subset of it. "Zone = 3 formats" is Puregold's current config; "Zone = geography" is just a second zone group in the same model. You never had to choose one or the other; JDA holds both. The naming collision ("Price Club" the company vs. the zone) also dissolves — the company is a COMPANY row, the zone is a ZONE row in the Format group. Different tables, same string.
